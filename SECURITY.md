# Security policy

## Threat model

Agent Orchestra Board is a local tool. It listens on `127.0.0.1` only and spawns the `claude` and `codex` CLIs under your own user account and your own logins. The things it protects are:

1. **Your files.** Seats are read-only unless you give a seat write permission and run a board build. A Claude write turn runs only in its item's detached git worktree under `.orchestra/worktrees/`, only after the write check has passed for that CLI on this machine, and with no shell tool. Codex never gets file edits in v0.2, on any platform: a Codex write seat builds in patch mode, a read-only turn whose diff the board checks and applies inside the item worktree. The board fingerprints the main checkout and the other worktrees around each builder turn. A change there quarantines the item and turns writes off for that CLI. The main checkout changes only when you apply a reviewed item, and then only staged: the board never commits. Read turns (Ask, Council, Propose → Review, the plan manager and every reviewer) can read the whole project, and the Codex read-only sandbox can read outside it too. The limits are listed under [Limits](#limits).
2. **Your browser as an attack path.** The attacker is a web page you have open, not someone on the network. Every request must carry a `Host` of exactly `localhost:<port>`, `127.0.0.1:<port>` or `[::1]:<port>` (DNS rebinding), any `Origin` must be `http://` one of those (cross-site fetch and XHR), and `POST` bodies must be `application/json` (no simple-form CSRF), at most 1 MB, with every field type- and length-checked. On top of that, every `/api/*` request needs the session cookie: a random 192-bit token, stored per project in `<project>/.orchestra/session` (mode 0600 on POSIX; on Windows it inherits the project folder's ACL) and printed in the start URL, exchanged on first load for an `HttpOnly; SameSite=Strict` session cookie named per port, compared in constant time. Responses carry a strict CSP (`default-src 'self'`, no framing, no external connections), `nosniff`, `no-referrer` and `no-store`. Static files are served only from `public/` after `path.resolve` and a prefix check. The version 2 routes (engines, runs, Ask, preflight) sit behind the same gate.
3. **Other local processes and users.** Without the token from your terminal they get `401` from the API; they can only see that the port is open.
4. **Your money.** Turns run against your Claude and Codex plans. Early stop and lean launches limit spend; per-seat token budgets do so only when set (off by default) and are checked before each turn, not during it. The write check is one turn of the chosen seat, and a build runs turns for every item and round. `doctor --containment` runs five short turns on cheap models, and only with `--yes`. The board runs the CLIs non-interactively: a Claude write turn uses `acceptEdits`, which approves file edits inside its worktree without a prompt. There is no per-edit confirmation step. Your review and your apply are the checkpoints.
5. **Scope of a seat.** A seat's target is confined to the project with `realpath` (no `..`, no absolute escapes, no symlinks pointing out); a target that resolves outside is rejected on save and ignored at run time.
6. **The project under review never supplies the CLI binary.** The board spawns the CLIs with the project (or a seat's target) as working directory, and on Windows libuv looks for a bare program name in the child's cwd before `PATH` unless `NoDefaultCurrentDirectoryInExePath` is set. Every child process of the board (`claude`, `codex`, the `--version` probes, the usage probe, `git`, `taskkill`, the browser opener) therefore goes through `platform.spawnResolved`, which resolves the name on `PATH` (or at the explicit `ORCHESTRA_*_BIN` path) and spawns the absolute file, or fails with "not found"; a `claude.exe` planted in a repository is never run. The board also sets `NoDefaultCurrentDirectoryInExePath=1` for itself on Windows (not for its children) as a second line, and `test/spawn.test.js` enforces that no other module spawns directly. `doctor` warns while `ORCHESTRA_CLAUDE_BIN` or `ORCHESTRA_CODEX_BIN` is set.
7. **Changes wait for your apply.** Each build item edits its own worktree. Its frozen proposal is hashed with sha256, and the review is bound to that hash; a worktree that changes after the freeze voids the review. Apply re-checks the patch hash, the owner areas, the dependencies, the plan approval, a clean checkout, the expected base commit and `git apply --check`, and then stages the change with `git apply --index`. Patches that add symlinks or submodules, or touch `.git`, `.orchestra` or paths outside the item's owner areas, are sent back before review, and apply refuses them again. Codex diffs pass the same checks, and also refuse absolute and `..` paths, before they are applied in a worktree.
8. **A write turn cannot widen itself.** Before a Claude write turn spawns, the board checks the real argv (no shell tool, no extra tools, `acceptEdits` exactly once, no `--add-dir`, `--settings`, `--mcp-config`, `--plugin-dir`, `--agents`, `--permission-prompt-tool` or skip and bypass flags, also in `--flag=value` form) and the worktree (registered, strictly inside `.orchestra/worktrees/`, not a link, equal to the turn's working directory, holding no symbolic link or junction). At the start of the turn the CLI's own report must list only the allowed tools, the worktree as its working directory, `acceptEdits` and no MCP server; anything else, or any event before that report, kills the turn and turns Claude writes off for the session. A write turn resumes only a thread born in the same worktree. No override of any kind (setting, flag, environment variable, seat field) turns Codex edits on or gives a Claude write turn a shell.
9. **Write check records cannot be planted by a project.** They live in one per-user file outside every project (`%APPDATA%\agent-orchestra-board`, `~/Library/Application Support/agent-orchestra-board` or `${XDG_CONFIG_HOME:-~/.config}/agent-orchestra-board`), are written atomically, and are bound to the CLI version, the platform, a hash of the board's write flags, the CLI binary (realpath, size, modification time), the host and the user. A `.orchestra/capability.json` in a repository is never read. A pass needs proof from the CLI's own tool log that it tried each outside write and was refused.
10. **Git in a worktree cannot be redirected.** The board never trusts a worktree's `.git` file: every git call on a board worktree passes `--git-dir` and `--work-tree` explicitly, and the worktree's `.git` file is hashed around each write turn. Worktrees are created with `core.symlinks=false`, so a symlink committed in the base checks out as a plain file. Hooks point at a path that never exists, and external diff, textconv, fsmonitor and signing are off.
11. **What the board reads of your other tools.** Runs and the external engines read Claude Code's and Codex's own files under `CLAUDE_CONFIG_DIR` (or `~/.claude`) and `CODEX_HOME` (or `~/.codex`), read only. Ids are checked before any file access, every path must resolve under the data folder, symbolic links are skipped, and only whitelisted fields are kept: no prompt or result text (previews of at most 400 characters are read on demand and never stored or broadcast), and never the account ids in Codex session metadata. All of that text is escaped before display.

Out of scope for v0.2: a compromised browser extension with host permissions, malware running as your user, multi-user or remote access, anything an agent does with the tools you explicitly granted it, and anything an external run does in your own CLI. The full threat model of the HTTP layer is in the header of `src/security.js`.

## Limits

* The write gate and the containment guard are detection and gating around the vendor CLIs. Containment inside a Claude write turn depends on the CLI's `acceptEdits` and tool flags. The board configures them and checks them, but it cannot prove them in general.
* **External runs are outside the gate.** *Claude Code, you run it* and *Codex, you run it* run in your own CLI with your own settings and can edit your checkout. The handoff asks for a worktree or branch and no commit, which is guidance only. On the development machine, 206 of 231 Codex sub-agents of past runs ran with full access. The board shows each sub-agent's sandbox and what changed; it prevents nothing.
* The guard fingerprints the main checkout, the board's worktrees and each worktree's `.git` file, around builder write turns only. It does not see ignored files, files outside the project, or a change that is undone before the turn ends.
* The guard's fingerprint of the main checkout excludes `.orchestra/`. A write that escapes into `.orchestra/` (the session token, the seats, the rooms, the proposals or the handoff files) is not detected.
* The write check is one prompt, run once. It shows what that CLI did on that machine in that run. Any drift (CLI version, binary, platform, write flags, host, user) voids it.
* Claude's real start-of-turn tool list has not been checked against the strict startup rule with a real CLI for this release. If it lists more tools than requested, Claude write turns stop before editing (fail closed). Whether a read-only board Codex seat can start sub-agents is also unverified. `doctor --containment` answers both and has not been run against the real CLIs for this release.
* Codex containment on macOS and Linux is untested on real machines. That is one reason Codex edits are off everywhere.

## Containment evidence

`doctor --containment` runs the real Claude and Codex CLIs on cheap models in a temporary repository. It reports whether writes stayed inside the worktree (inside, absolute, `../`, prefix sibling, `CANARY.txt`, the worktree's `.git` file, links, Windows `\\?\` and UNC paths) and whether a read-only Codex seat can start sub-agents. It prints its plan first, runs only with `--yes`, never touches your project and never writes a check record.

Result on 2026-10-08, Windows 11, claude-code 2.1.291 and codex-cli 0.160.0:

* **Claude: inconclusive.** The model did not attempt the write outside the worktree, so the run cannot show that the CLI refused it.
* **Codex: direct writes stay off on every platform.** Codex works through patch mode, so the board applies its diffs inside the item worktree. Codex sub-agents can start even with `features.multi_agent=false`, and they inherit the parent's read-only policy.

Codex sandbox behavior is being handled in a private report to OpenAI, so this section does not describe it further. Neither result is evidence for macOS or Linux. Run the command on your own machine to get evidence there.

## Supported versions

Only the latest release on `main` receives fixes.

## Reporting a vulnerability

Please do not open a public issue for a security problem. Use GitHub's private vulnerability reporting on the repository ("Security" tab, "Report a vulnerability"). If that is not available, open an issue titled "Security contact request" without details and a maintainer will reply with a private channel.

Include: the version or commit, your OS, the request or steps that reproduce it, and what you believe the impact is. You should get an acknowledgement within 7 days. Fixes ship as a patch release with a CHANGELOG entry; we will credit you unless you prefer otherwise.

## Hardening tips

* Never put the port behind a tunnel, reverse proxy or `0.0.0.0` bind; the session cookie is sent over plain HTTP and is only safe on the loopback interface.
* Treat the printed start URL like a password for that project: do not paste it into chats or screenshots. It stays valid across restarts; delete `<project>/.orchestra/session` to rotate it.
* Run the write check after installing or upgrading Claude Code. Allow a Claude seat to edit files in Build worktrees only after its CLI passes.
* If you want evidence for your own machine, run `agent-orchestra-board doctor --containment` once, read its plan, then add `--yes`. It costs a few cents and touches only a temporary folder.
* Review every proposal before you apply it, and read exported patches and Codex diffs with extra care: they are untested. Apply stages the change. Check `git diff --cached` before you commit, and run `git restore --staged` on the paths if you change your mind.
* Run external engines in a clean checkout, and check `git status` and `git worktree list` after the run; the run card's change summary is a start, not a review.
* Do not edit the main checkout while a write build runs. The guard reads that as a change outside the worktree and quarantines the item.
* Commit or ignore `<project>/.orchestra/` deliberately. Room transcripts can contain file contents a scout read, and `proposals/`, `handoff/` and `worktrees/` hold your code and plans. `.orchestra/session` holds the board's session token and must never be committed. The board writes a `.orchestra/.gitignore` that lists `session` and `worktrees/` on first start; do not remove those entries.
* Run `agent-orchestra-board doctor` (or `node bin/agent-orchestra-board.js doctor`) after upgrading either CLI; adapters parse undocumented stream formats.
